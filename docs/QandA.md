# Q&A

This file captures recurring questions and answers discussed during development so future contributors can reference decisions quickly.

## Q: Is `ReplayBuffer` the same as a trajectory?
A: No. The replay buffer stores **individual transitions** `(s, a, r, s', done)` and does not preserve episode order. A trajectory is an **ordered sequence** of transitions. The buffer may contain pieces of trajectories, but it is not itself a trajectory.

## Q: Does PettingZoo replace PyTorch or do learning/inference?
A: No. PettingZoo is only the **environment API**. Learning/inference is done by an RL algorithm (custom DQN, SB3, RLlib) implemented separately, typically using a deep learning framework like PyTorch.

## Q: If I switch to an RL library, does the environment need to change?
A: Usually no. As long as `SwarmEnv` follows the PettingZoo Parallel API, you can swap the learning backend without changing the environment. You may add wrappers if a library expects a different API.

## Q: Is inference the same across RL libraries?
A: No. Each library saves models differently and has its own load/predict API. A unified demo script can route to the correct loader based on `--backend`.

## Q: Is `swarm_env.py` “RL code”?
A: It is the **environment** that defines the MDP: observations, actions, rewards, and termination. It does not learn. The training code is separate.

## Q: In sim-to-real transfer, is `_get_obs()` the key interface?
A: Largely yes: `_get_obs()` maps world state to the observation vector the policy uses. On a robot, the equivalent is the **sensor preprocessing pipeline** that produces the same vector. You also need an **action interface** that maps actions to motor commands.

## Q: Does `_handle_targets` reward agents based on distance, and how would this work in the real world?
A: In the sim, `_handle_targets()` gives a reward **only when a target is collected** (within the target radius). It does **not** reward based on distance. In the real world, you’d need a **detectable target** (e.g., marker/vision/RFID) so the robot can confirm contact, or you’d change the task so rewards come from its own sensors (e.g., signal strength/proximity). The observation pipeline must be built from real sensors, and “target collected” must be detectable by the robot.

## Q: If reward depends on a target radius, does the environment need to know target locations?
A: In simulation, yes—the environment tracks target positions to determine if an agent is within the collection radius. That’s not necessarily distance-shaped reward; it’s a **binary “collected” check**. In the real world, the equivalent is a **target detection signal** from sensors, not a hidden oracle.

## Q: What needs to change for real-world deployment?
A: See `docs/ToDo.md` for a required-change checklist covering sensors/observations, action interface, target detection, reset procedures, safety, domain gap mitigation, runtime loop, and logging.

## Q: What does it mean that the env is PettingZoo-native?
A: It means `SwarmEnv` implements the **PettingZoo Parallel API** directly (dict-based `reset()` and `step()` with per-agent observations/rewards/terminations). You can plug it into PettingZoo-compatible tooling without extra wrappers.

## Q: What does MLP stand for?
A: **Multi-Layer Perceptron** — a standard feedforward neural network with fully connected layers.

## Q: Do SB3/RLlib do the training themselves or use an underlying DL library?
A: They **do the training**, but they are built on top of a deep learning framework. SB3 uses **PyTorch**. RLlib supports **PyTorch** (and sometimes other backends). The library manages the RL algorithm loop; the DL framework handles neural nets and gradients.

## Q: What’s the relationship between PettingZoo, SB3/RLlib, and PyTorch?
A: PettingZoo is the **environment API** (multi-agent interface). SB3/RLlib are **RL training libraries** that implement algorithms and use environments. PyTorch is the **deep learning backend** used by those libraries to build and train neural networks. In short: PettingZoo (env) → SB3/RLlib (RL algorithm) → PyTorch (NNs/gradients).

## Q: Is a Q-function a policy?
A: Not exactly. A **Q-function** estimates how good an action is in a state. A **policy** chooses actions. In DQN, the policy is derived from the Q-function by taking `argmax_a Q(s, a)` (often with epsilon-greedy exploration).

## Q: Are `batch_size`, `lr`, and `epsilon_*` for stochastic batch gradient descent?
A: **Partly.** `batch_size` and `lr` control the **stochastic gradient descent** updates (how many samples per update, how big each step is). `epsilon_*` is **not** about gradient descent; it controls **exploration** in the policy (random action rate), not the optimizer.

## Q: What does "PettingZoo Parallel" mean?
A: It refers to PettingZoo's **Parallel API** for multi-agent environments. All agents act at the same timestep, and `step()` takes a dict of actions for all active agents, then returns dicts of observations, rewards, terminations, truncations, and infos keyed by agent ID.

## Q: How should I learn this project from scratch as a beginner?
A: Start with this sequence: (1) RL basics and terms, (2) environment/MDP in `env/swarm_env.py`, (3) custom DQN training in `train/independent_dqn_pytorch.py`, (4) inference in `train/demo.py`, (5) backend switching via `train/train.py` (custom/SB3/RLlib), then (6) sim-to-real considerations in `docs/ToDo.md`.

## Q: For sim-to-real transfer, what should we pay attention to during training?
A: Focus on **domain gap**: match observation normalization and action scaling, add sensor/dynamics noise, include delays, and train with randomized environments. Consider safety penalties and curriculum training. These items were added to `docs/ToDo.md`.

## Q: Can you teach me the code and the RL flow in this repo?
A: Start from `env/swarm_env.py`: that file is the environment and defines the RL problem through `reset()`, `step()`, observations, rewards, and episode endings. Then read `train/independent_dqn_pytorch.py`: that file is the learning loop that collects transitions, stores them in replay buffers, samples minibatches, computes Bellman targets, and updates Q-networks. `train/train.py` is only a dispatcher that picks the backend (`custom`, `sb3`, or `rllib`), and `train/demo.py` is inference-only for running trained checkpoints.

## Q: Can you explain RL concepts for a beginner by mapping them directly to this repo?
A: Yes. In this repo, the **environment/MDP** is `env/swarm_env.py`, the **state/observation** is the vector built by `_get_obs()`, the **action space** is the 9-way discrete table from `_build_action_table()`, the **reward** is computed in `step()` and `_handle_targets()`, the **policy/value model** is `QNetwork` in `train/independent_dqn_pytorch.py`, and the **learning loop** is `train()` in that same file. The easiest way to learn RL here is to follow one cycle: observation → action selection → `env.step()` → reward/next observation → replay buffer → Bellman update.

## Q: How should we architect sim-to-real deployment on a Raspberry Pi with an Arduino sensor/motor layer while minimizing code changes?
A: Keep the learned policy and observation/action shapes unchanged as much as possible. Put a **real-world adapter** on the Raspberry Pi that replaces the simulator’s `_get_obs()` and `step()` side effects: it should read fused sensor data from the Arduino and Pi-side estimators, build the same normalized observation vector the policy expects, run inference, and send a high-level action command to a low-level controller. The Arduino should remain a real-time I/O layer for sensors and motor control, while the Pi stays the policy/runtime “brain.” Use a small message contract such as `sensor_packet -> observation_builder -> policy_inference -> action_command -> motor_controller`, with safety overrides outside the policy.

## Q: What files implement the first sim-to-real deployment skeleton in this repo?
A: The detailed design is documented in `docs/SimToReal.md`. The Pi-side runtime skeleton lives in `robot/`: `sensor_bridge.py` reads `SensorPacket` data, `observation_builder.py` converts packets into policy observations, `policy_runner.py` loads the trained DQN checkpoint and runs inference, `action_bridge.py` maps actions into high-level commands, and `runtime.py` connects the loop together. This keeps `env/` and `train/` largely unchanged.

## Q: Can you explain `QNetwork`, the Bellman update, and one full training iteration in this repo together?
A: Yes. `QNetwork` in `train/independent_dqn_pytorch.py` is a small MLP that maps one observation vector to one Q-value per discrete action. The Bellman target in `train()` is `reward + gamma * max_a' Q_target(next_obs, a')` unless the episode ended, and training minimizes the gap between that target and the current `Q(obs, action)`. One full training iteration is: build actions with epsilon-greedy, call `env.step()`, store transitions in replay, sample random minibatches after warmup, compute Bellman targets, update the online network, and periodically copy weights to the target network.

## Q: Where is the standalone doc that explains `QNetwork`, the Bellman update, and one full training iteration?
A: See `docs/DQN_EXPLAINED.md`. It consolidates the explanation of tensor shapes, the Bellman target used in the custom trainer, and the step-by-step control flow of one training iteration in `train/independent_dqn_pytorch.py`.

## Q: What are `custom`, `sb3`, and `rllib`, and when should I pick each one?
A: They are the three training backends selected by `train/train.py`. `custom` runs the repo’s own PyTorch DQN trainer in `train/independent_dqn_pytorch.py`, which is the easiest option for learning and modifying the algorithm. `sb3` runs Stable-Baselines3 DQN through `train/sb3_dqn.py`, which is simpler than RLlib and useful when you want a standard library implementation with fewer moving parts. `rllib` runs Ray RLlib DQN through `train/rllib_dqn.py`, which is heavier but more suitable when you want richer multi-agent/distributed tooling. In this repo, start with `custom` for understanding and experiments, use `sb3` when you want a cleaner library baseline, and reach for `rllib` only if you specifically need Ray/RLlib capabilities.

## Q: Is the sim-to-real runtime basically the same as the custom demo inference loop?
A: Yes, for the policy portion it is very close. The key pieces in `train/demo.py` are loading the model, building `obs_tensor`, running the network to get Q-values, taking `argmax` to choose the action, and then handing that action to a downstream executor. In sim, the downstream executor is `env.step(...)`; on the robot, it should be a real-world action bridge that translates the chosen action into physical commands. The main extra requirement is that the Pi must build observations from real sensors with the same feature order and normalization the model was trained on.

## Q: What does `--headless` do in training?
A: It runs the environment without opening a PyGame window. In `SwarmEnv.__init__`, `headless=True` sets `render_mode=None`, `render()` becomes a no-op, and screenshot saving is disabled. The environment logic, observations, rewards, and stepping still run normally; only on-screen rendering is skipped. This is the normal mode for faster training and evaluation.

## Q: Why save checkpoints during training?
A: Checkpoints let you keep intermediate versions of the learned policy instead of only the final one. In this repo that is useful for at least four reasons: you can resume or inspect a run if training stops early, you can demo or evaluate earlier models without retraining, you can compare model quality across training stages, and you avoid losing all progress from a long run if something crashes. They are especially useful now that training/evaluation and experiment scripts can load saved models later.

## Q: In `train/independent_dqn_pytorch.py`, what does `--save-dir checkpoints` do, and what happens if I do not pass it?
A: `--save-dir` tells the trainer where to write checkpoint files. In the current code its default is already `checkpoints`, so if you do not pass `--save-dir`, it still saves to the `checkpoints/` folder. The separate `--save-every` flag controls whether intermediate checkpoints are also written during training. Even if `--save-every` is left at its default `0`, the trainer still saves one final checkpoint at the end into `args.save_dir`.

## Q: Can you walk me through training in `train/independent_dqn_pytorch.py`?
A: Yes. The file follows a standard DQN structure. `parse_args()` defines the CLI, `train(args)` builds the environment and run directory, infers `obs_dim` from `env.reset()`, creates either independent or shared `QNetwork` instances plus matching target networks, optimizers, and replay buffers, then enters the main loop. Each loop iteration computes epsilon, selects one action per agent with epsilon-greedy, steps the environment, stores `(obs, action, reward, next_obs, done)` into replay, and after warmup samples minibatches to apply the Bellman update with Huber loss. Every `target_update` steps it syncs target networks, optionally runs `_evaluate_policy()`, logs episode metrics when an episode ends, optionally saves checkpoints during training, and always saves final checkpoints plus `summary.json` at the end.

## Q: What does `train/evaluate.py` do?
A: It runs headless evaluation episodes and writes evaluation metrics; it does not train. It builds a `SwarmEnv`, infers `obs_dim` from `env.reset()`, then either loads custom DQN checkpoints with `_load_models(...)` or builds rule-based policies with `_build_rule_based_policies(...)`. For each evaluation episode it resets the env with a deterministic seed, runs greedy action selection (`argmax` over Q-values for DQN, `.act(obs)` for rule-based), steps the env until termination/truncation, accumulates metrics like mean reward, food retrieved, exploration coverage, pheromone usage, episode length, and swarm efficiency, logs one row per episode to `eval_metrics.csv`, and finally writes aggregated means to `eval_summary.json`.

## Q: What does `train/policy_probe.py` do?
A: It is a small CLI inspection tool for the repo’s custom PyTorch DQN checkpoints. You give it a checkpoint directory plus a hand-written observation case, and it loads either `shared.pt` or `agent_<i>.pt`, detects whether the checkpoint expects the current 23-D observation layout or an older 19-D layout, runs one forward pass through `QNetwork`, prints the labeled observation values and all 9 action Q-values, then reports the greedy chosen action with a short heuristic plain-English explanation. It is for probing and teaching model behavior on fixed example observations, not for training or full environment rollouts.

## Q: What do the observation values in `train/policy_probe.py` mean?
A: They are the policy’s input features: a numeric snapshot of what one agent “knows” at one moment. In the current 23-D layout, `lidar_0` to `lidar_8` are normalized obstacle-distance readings around the agent, with higher values meaning more open space and `lidar_4` acting as the front-center reading. `target_dx_body_norm` and `target_dy_body_norm` are the normalized target direction in the agent’s body frame, while `nest_dx_body_norm` and `nest_dy_body_norm` give the nest direction the same way. `neighbor_dx_body_norm` and `neighbor_dy_body_norm` describe the nearest neighbor’s relative direction. `heading_sin` and `heading_cos` encode orientation as `sin(theta)` and `cos(theta)`. `speed_norm` is normalized speed. `food_presence` indicates whether food is locally present, `carrying_food` indicates whether the agent is carrying food, and `pheromone_sample_0` to `pheromone_sample_2` are normalized pheromone strengths. The important point is that these are mostly normalized local cues in the agent’s own frame, not raw world coordinates. Older checkpoints may instead use the legacy 19-D layout, which drops the nest-direction, `food_presence`, and `carrying_food` features.

## Q: How do I translate the normalized observation values into millimeters?
A: The sim does not define an intrinsic millimeter scale; its geometry is expressed in environment world units, which also match the render coordinates. So there are two cases. If you only want to undo the normalization back into sim-distance units, multiply normalized distance-like features by `cfg.lidar_max_range`, which is currently `160.0`. That means `lidar_i * 160`, `target_dx_body_norm * 160`, `target_dy_body_norm * 160`, `nest_dx_body_norm * 160`, `nest_dy_body_norm * 160`, `neighbor_dx_body_norm * 160`, and `neighbor_dy_body_norm * 160` recover the underlying body-frame distances in sim units, clipped to `[-160, 160]` for vectors and `[0, 160]` for lidar. If you want millimeters, you must additionally choose a calibration such as “1 sim unit = 10 mm,” then multiply by that scale: `mm = normalized_value * 160 * mm_per_sim_unit`. `speed_norm` similarly converts back to sim speed with `speed_norm * cfg.max_speed`, where `cfg.max_speed` is currently `120.0`; then convert that sim speed to mm/s with your chosen scale. `food_presence` and `carrying_food` are binary flags, `heading_sin` and `heading_cos` are trigonometric orientation values rather than distances, and pheromone samples are relative normalized intensities, not physical length units.

## Q: What millimeter scale would you recommend for this sim?
A: I would start with `1 sim unit = 10 mm` as the default calibration. That makes the current config values land in a reasonable small-robot regime: `agent_radius=10` becomes a 100 mm radius robot (about 200 mm diameter), `lidar_max_range=160` becomes 1600 mm sensing range, `food_presence_radius=120` becomes 1200 mm, and the `900 x 600` world becomes `9.0 m x 6.0 m`. Those numbers are coherent for an indoor tabletop or lab-floor swarm setup and are also close to the current direct robot runtime in [firmware/run.py](../firmware/run.py), which uses millimeter-scale move commands such as `100` mm forward steps. If your actual robot is materially smaller or larger, anchor the scale to physical robot diameter first: `mm_per_sim_unit = real_robot_radius_mm / cfg.agent_radius`.

## Q: What scale mapping does `firmware/run.py` use?
A: The current runner uses millimeters directly for the real robot and a fixed normalized observation scale for the policy. Lidar readings arrive from `ant.py` as `tof_mm`, are bucketized, then converted to meters and normalized by `lidar_max_range_m`, which defaults to `1.6` meters from `--lidar-max-range-mm 1600`; the normalized lidar fed to the network is `2 * clip(range_m / 1.6, 0, 1) - 1`, so `-1` means very close and `+1` means max range or farther. The target, nest, neighbor, speed, and pheromone channels are currently hardcoded placeholder zeros in this file, with heading fixed to `[0, 1]`. On the output side, the discrete 9-action policy is mapped to direct robot commands with `turn_step_deg=25`, `move_distance_mm=100`, and `reverse_distance_mm=60` by default: turn-only actions send `robot.turn(±25)`, forward actions send `robot.move(0, 100)`, reverse actions send `robot.move(180, 60)`, and the center action sends `robot.stop()`. This file does not apply any separate sim-unit-to-mm calibration beyond the explicit `--lidar-max-range-mm`, `--move-distance-mm`, and `--reverse-distance-mm` arguments.

## Q: Does `firmware/run.py` treat TOF `-1` as out-of-range / far, like `main()` in `ant.py`?
A: Yes. In `bucketize_scan(...)`, any scan with `tof_mm < 0` is skipped, and each lidar bucket is initialized to `max_range_mm` first. That means a `tof_mm` of `-1` never overwrites the bucket, so the bucket stays at max range and is later normalized as “far” (`+1` after normalization). So the effect matches `main()` in `ant.py`, which explicitly treats `distance == -1` as free space. The difference is only implementation style: `ant.py` checks `distance == -1` directly, while `run_policy.py` handles it implicitly by ignoring negative readings and leaving the default max-range value in place.

## Q: What is the mm-to-units relationship in `firmware/run.py`, and how do I tweak it?
A: In the current firmware runner there is no separate hidden sim-unit conversion layer. The real robot side works in explicit physical units you pass on the CLI. `--lidar-max-range-mm` sets the distance scale used to normalize TOF readings before inference; by default `1600` mm becomes `1.6` m in `PolicyConfig.lidar_max_range_m`, and normalized lidar is computed relative to that range. `--move-distance-mm` and `--reverse-distance-mm` set the commanded forward and reverse step sizes in millimeters, and `--turn-step-deg` sets the commanded turn amount in degrees for one discrete turn action. If you want to tweak the scale, change those CLI arguments at runtime, or change their defaults in `parse_args()` in `firmware/run.py`. If you are asking about the original simulator calibration, the repo’s documented recommendation is still `1 sim unit = 10 mm`, but this particular file no longer uses sim units directly; it only uses the explicit mm and degree values above.

## Q: Given a real robot radius of 70 mm, what should the sim-unit scale be?
A: Using the repo’s calibration rule `mm_per_sim_unit = real_robot_radius_mm / cfg.agent_radius`, and the current `cfg.agent_radius = 10`, the scale should be `70 / 10 = 7 mm` per sim unit. So `1 sim unit = 7 mm`, and the existing simulated robot radius of `10` units would correspond to a real 70 mm radius robot. If you instead want to keep the older `1 sim unit = 10 mm` scale, you would need to change the simulated `agent_radius` to `70 / 10 = 7` units instead.

## Q: Where do I find the sim-unit calibration info?
A: The current simulated robot radius is defined at [env/config.py](../env/config.py#L14) as `agent_radius = 10.0`. The calibration guidance and formulas are documented in [docs/QandA.md](QandA.md): the normalized-to-mm explanation is around line 144, the recommended baseline `1 sim unit = 10 mm` is around line 147, and the specific 70 mm radius calculation (`1 sim unit = 7 mm`) is at [docs/QandA.md](QandA.md#L161).

## Q: Would `agent_radius = 7` and `target_radius = 3` work?
A: Yes, if you are choosing to keep the calibration `1 sim unit = 10 mm`. Under that scale, `agent_radius = 7` represents a 70 mm robot radius, and `target_radius = 3` represents a 30 mm target radius. That is mechanically consistent. The real question is whether a 30 mm target radius matches your physical target size and the tolerance you want for pickup/contact in the task. If your real target is larger or if detection/contact is noisy, you may want a larger `target_radius` such as `4` or `5` instead. So `7` and `3` will work as a calibration choice, but `3` is a task-design decision rather than something implied by the robot size alone.

## Q: How does `comms` communicate with each robot?
A: The `comms` layer uses line-oriented direct links, not a shared broadcast bus. ## Q: What is a good pheromone radius for each robot to be aware of?
A: For the current codebase, the best default is to keep the existing training-compatible forward sampling radius rather than invent a new one ad hoc. The effective awareness radius is set by three forward samples at distances `(i + 1) * agent_radius * 1.5`, so the farthest sample is `4.5 * agent_radius`. With the current default [env/config.py](../env/config.py) value `agent_radius = 7.0`, that means a maximum forward pheromone awareness distance of `31.5 cm` when the Mission Control scale is `1 sim unit = 1 cm`. That is a reasonable local-following radius because it is only a few body lengths ahead and matches the observation contract the model was trained on. If you want a rule-of-thumb range for future tuning, stay around `3` to `5` body radii for local trail following; beyond that, the robot stops behaving like it is following a local cue and starts acting on more global field structure. In this repository, changing that radius without retraining would break observation compatibility, so the practical recommendation is: keep the current `4.5 * agent_radius` maximum unless you also retrain and update both [env/swarm_env.py](../env/swarm_env.py) and [mission_control/core/pheromone_field.py](../mission_control/core/pheromone_field.py).

## Q: What structure should the pheromone data use if it needs to work for both the Raspberry Pi runtime and the command center?
A: I would separate this into a shared immutable contract plus one authoritative store. The authoritative pheromone field should stay in [mission_control/core/pheromone_field.py](../mission_control/core/pheromone_field.py), because that side already owns decay, diffusion, and simulator-compatible forward sampling. The Raspberry Pi side should not mirror the whole grid as its primary state; it should treat Mission Control as the source of truth and consume a small observation-facing structure such as: robot pose input `(robot_id, x_cm, y_cm, heading_deg)`, deposit events `(robot_id, x_cm, y_cm, amount, timestamp)`, and sampled response `(robot_id, sample_values[3], timestamp, field_version)`. The shared contract should also carry the geometry parameters that must match training: `cell_size_cm`, `pheromone_samples`, sample distance rule, normalization rule, and coordinate frame. In code terms, I would put that shared schema and math in a small common module such as `shared/pheromone_contract.py` with dataclasses for config, query, deposit, and response, plus pure helper functions for coordinate-to-cell mapping and forward sample geometry. Then `mission_control/` would own the mutable grid implementation, while `firmware/` would only send `deposit` / `sense` requests and receive normalized sample vectors that drop directly into the observation slots documented in [docs/OBSERVATION_SPEC.md](OBSERVATION_SPEC.md). That keeps the behavior aligned without creating two competing pheromone-field implementations.

## Q: Is it possible for the policy to learn to drop pheromone?
A: Yes, but not in the current action design. Right now the learned policy only chooses among 9 movement actions because [env/config.py](../env/config.py) sets `num_actions = 9`, and [env/swarm_env.py](../env/swarm_env.py) builds the action table as the Cartesian product of throttle `{-1, 0, 1}` and turn `{-1, 0, 1}`. In the live robot path, pheromone dropping is currently added afterward as runtime logic in [firmware/run.py](../firmware/run.py), not as a policy output. So it is definitely possible for the policy to learn it, but that would require changing the action space or policy head so “deposit pheromone” becomes part of the agent’s decision, then training under that new interface with rewards/objectives that make deposition strategically useful. A clean version would be either: expand the discrete action space to include deposit variants of movement actions, or make the policy output movement plus a separate binary deposit decision. Until that refactor happens, the current policy can learn to exploit pheromone observations, but it cannot explicitly learn when to deposit because deposit is not one of its learned actions.

## Q: How do Mission Control and the robot connect, and can Mission Control connect to multiple robots?
A: Mission Control supports multiple transport backends, but the wire protocol is the same in all cases: newline-delimited ASCII messages like `POS`, `PHER`, `SENSE`, and `PHER_RESP`. In the current live robot path, [firmware/bluetooth.py](../firmware/bluetooth.py) makes the Raspberry Pi act as a BLE client and connect to desktop Mission Control's BLE peripheral exposed by [mission_control/comms/receiver.py](../mission_control/comms/receiver.py). Mission Control can also listen over TCP or serial from [mission_control/main.py](../mission_control/main.py). For TCP, yes, Mission Control is explicitly designed for multiple robots: each incoming TCP client gets its own worker thread, and traffic is isolated per connection. For serial, yes, if you pass multiple serial ports, each port gets its own worker. For BLE, the transport now supports multiple robots by multiplexing them over the shared BLE line channel using `robot_id`: Mission Control derives a logical per-robot label from each incoming message, and replies still include `robot_id` so each Pi-side BLE client can ignore responses for other robots. The result is that Mission Control can now support multiple robots over BLE too, but the isolation model is protocol-level multiplexing rather than one dedicated BLE worker thread per robot like the TCP path.

## Q: Does the current training process just place pheromone wherever the robot goes?
A: In the simulator training environment, effectively yes. ## Q: If two pheromones from separate robots overlap, do they add up, and do they last longer?
A: Yes, overlapping pheromone deposits add up in the current Mission Control field. In [mission_control/core/pheromone_field.py](../mission_control/core/pheromone_field.py), each deposit uses `+=` on the affected cells, so if two robots deposit into the same cell or overlapping circular region, the values accumulate. Decay is then applied multiplicatively to the whole grid via `self.grid *= self.cfg.decay_factor`, with the default factor coming from [mission_control/config.py](../mission_control/config.py) and ultimately [env/config.py](../env/config.py). So overlap does not change the decay rate itself, but it does make the resulting pheromone stronger, which means it takes longer in absolute time to decay back down near zero. Diffusion then spreads that stronger signal into neighboring cells as usual. So the correct interpretation is: yes, the values add; no, the decay coefficient does not slow down; but yes, a larger accumulated value persists longer before becoming negligible.

## Q: In `firmware/run.py`, if the starting position is the nest at the origin, how do I calculate `x` and `y` displacement?
A: The current [firmware/run.py](../firmware/run.py) does not track pose; it only sends turn and move commands. To compute displacement from the nest, maintain `(x, y, theta)` locally with initial state `(0, 0, theta_0)`. Because `execute_action(...)` turns first and then moves, update heading before translation: `theta_{t+1} = theta_t + turn * turn_step_deg * pi / 180`, where `turn` is `-1`, `0`, or `+1`. Then set step distance `d = move_distance_mm` for forward actions, `d = -reverse_distance_mm` for reverse actions, and `d = 0` for no-translation actions. Using the repo’s standard world-frame convention `x += cos(theta) * d`, `y += sin(theta) * d`, the displacement update is `x_{t+1} = x_t + d * cos(theta_{t+1})` and `y_{t+1} = y_t + d * sin(theta_{t+1})`. If you assume `theta_0 = 0`, then the nest-relative displacement starts along `+x`. Pure turn actions change `theta` only; the center stop action changes neither `theta` nor position.

## Q: Is the current RL deterministic or stochastic?
A: Both, depending on which part you mean. The custom trainer in [train/independent_dqn_pytorch.py](../train/independent_dqn_pytorch.py) is **stochastic during training** because it uses epsilon-greedy exploration (`random.random() < epsilon`) and random replay-buffer sampling. The learned policy is **deterministic at inference/evaluation time** because action selection uses `argmax` over Q-values in [train/demo.py](../train/demo.py), `train/evaluate.py`, and `_evaluate_policy()` in the trainer. The environment in [env/swarm_env.py](../env/swarm_env.py) also contains randomness in world spawning and, if hover or mixed dynamics are used, hover noise/slip. With the default config in [env/config.py](../env/config.py), `dynamics_mode="tank"` and `observation_noise_std=0.0`, so step dynamics are deterministic given the same seed and same action sequence, but resets still randomize the world unless you fix the seed.

## Q: Is the deployed robot-side inference model deterministic?
A: Yes. The active robot runtime in [firmware/run.py](../firmware/run.py) loads a checkpoint and chooses the action with `torch.argmax(q_values, dim=1)`, so for the same model weights and the same observation vector it will choose the same discrete action every time. Any non-repeatability on the robot would come from changing sensor inputs, hardware timing, actuator error, or added randomness elsewhere, not from stochastic sampling in the policy itself.

## Q: Is it hard to make the deployed robot policy stochastic, and can that be done without changing the interface?
A: No, it is not hard. You can keep the same observation vector, the same checkpoint format, and the same robot-side output contract of “one discrete action ID,” and only change the internal action-selection rule. The standard options are: (1) **epsilon-greedy inference**, where the policy picks a random action with probability `epsilon` and otherwise uses the current greedy action; (2) **softmax/temperature sampling** over the Q-values, where you convert Q-values into action probabilities and sample one action; or (3) **adding small noise to the Q-values before `argmax`**, which preserves the same output interface but is less standard. In all three cases the robot can keep using essentially the same code path because the interface remains observation-in, discrete-action-out. The main tradeoff is behavioral quality: DQN is normally deployed greedily, so adding runtime stochasticity is mechanically easy but can reduce stability or efficiency unless the randomness level is tuned carefully.

## Q: What does `firmware/run.py` do?
A: It is the live robot-side inference loop. It parses runtime flags, loads a trained `QNetwork` checkpoint (`shared.pt` or `agent_0.pt`), connects to the robot over serial via `ESP32Robot`, reads scan data for each control step, converts the scan into the policy’s observation vector, runs one forward pass, chooses the greedy discrete action with `argmax`, maps that action into turn/move/stop commands, and sends those commands to the robot at the requested loop rate. In debug mode it also prints startup settings, per-step scan counts, normalized lidar values, chosen action, and Q-values.

## Q: How should the robot-side `firmware/` code be structured to support Bluetooth communication with the command center?

## Q: What MARL setup is this repo actually using?
A: The main training path in [train/independent_dqn_pytorch.py](../train/independent_dqn_pytorch.py) is independent multi-agent DQN over a shared PettingZoo parallel environment, not a centralized-critic method like QMIX, MADDPG, or MAPPO. Each agent receives its own local observation vector from [env/swarm_env.py](../env/swarm_env.py), selects one discrete action, stores its own transition in its own replay buffer, and learns a standard single-agent Bellman target with its own target network. If `--shared-policy` is off, the code creates one separate `QNetwork` per agent and saves `agent_0.pt`, `agent_1.pt`, and so on. If `--shared-policy` is on, all agents reuse the same `QNetwork` weights but still act from their own local observations and write separate replay entries. Coordination is therefore implicit rather than explicitly modeled: agents interact only through the shared world dynamics, rewards, obstacles, targets, nest-delivery mechanics, and pheromone field inside [env/swarm_env.py](../env/swarm_env.py). The network itself is a simple per-agent MLP in [models/q_network.py](../models/q_network.py), and there is no joint action-value mixer, no centralized state input, and no communication channel learned between agents.

## Q: Why does `train/demo.py` fail with a `size mismatch` on `net.4.weight` after the pheromone-action change?

The practical fixes are: either retrain with the new 18-action interface and load those new checkpoints, or temporarily revert the environment/action config back to the old 9-action setup if you need to run legacy checkpoints unchanged.

## Q: How do I encourage more random exploration at the start of training?
A: The current trainer already starts fully random: in [train/independent_dqn_pytorch.py](../train/independent_dqn_pytorch.py), `DQNConfig.epsilon_start = 1.0`, and action selection uses `if random.random() < epsilon: actions[i] = np.random.randint(0, action_dim)`. So at step 0 the policy is taking random actions all the time. If you want that exploratory phase to last longer, the main knob is `epsilon_decay_steps`, which is currently `8000`; increasing it makes epsilon stay high for more steps. A second knob is `warmup_steps`, currently `500`, which delays gradient updates so the replay buffer fills with more exploratory experience before learning starts. On the environment side, [env/config.py](../env/config.py) has `reward_exploration = 0.02`, so you can also increase that reward slightly if you want the task itself to value visiting new cells more strongly. The practical summary is: the start is already random; to make it *stay* random longer, raise `epsilon_decay_steps` and optionally `warmup_steps`, and to make exploration more attractive, raise `reward_exploration`.

## Q: How do I make training start very random and then become less random over time?
A: The main trainer now exposes the epsilon-greedy schedule directly on the CLI in [train/independent_dqn_pytorch.py](../train/independent_dqn_pytorch.py). Use `--epsilon-start` for how random the policy is at the beginning, `--epsilon-final` for how random it remains late in training, `--epsilon-decay-steps` for how slowly it anneals from the start value to the final value, and `--warmup-steps` for how long the replay buffer should be filled before learning updates begin. A typical "very random at the start, then less random" run is: `python train/independent_dqn_pytorch.py --headless --total-steps 10000 --epsilon-start 1.0 --epsilon-final 0.05 --epsilon-decay-steps 9000 --warmup-steps 1000`. Larger decay and warmup values keep early training more exploratory; smaller values make it settle faster.

## Q: Why does `train/demo.py` look the same every time I launch it?
A: The current demo is deterministic across separate launches unless you change the seed. In [train/demo.py](../train/demo.py), `--seed` defaults to `0`, and the first environment reset in `main()` always uses `env.reset(seed=args.seed)`. That means every fresh run starts from the same initial random state unless you pass a different `--seed`. The code was already updated so later episode resets within the same run use incrementing seeds (`args.seed + 1`, `args.seed + 2`, and so on), which makes episodes vary after the first one, but a brand-new process still repeats the same first setup if you keep the default seed. To vary launches, run something like `python train/demo.py --checkpoint-dir checkpoints_new --seed 42`, then change the seed on the next run.

## Q: Does the training seed change during training?
A: Yes, but in a specific way. In [train/independent_dqn_pytorch.py](../train/independent_dqn_pytorch.py), the very first environment reset uses `env.reset(seed=args.seed)`, so the run starts from the CLI seed you passed. After that, episode resets advance through `next_reset_seed = args.seed + 1` and then call `env.reset(seed=next_reset_seed)` each time an episode ends, incrementing that seed after every reset. So within one training run, episode setups do change over time. What does not change automatically is the base seed for a fresh launch: if you rerun training with the same `--seed`, the sequence of episode seeds will be reproducible. Evaluation is similar: `_evaluate_policy(...)` resets with `base_seed + episode`, so each evaluation episode also uses a distinct but deterministic seed.

## Q: Why do the robots in `train/demo.py` seem to get stuck after a few steps?
A: The main reason is that the demo runs a fully greedy policy with no exploration. In [train/demo.py](../train/demo.py), action selection is `torch.argmax(...)`, so once the network finds a locally preferred action pattern, it repeats it exactly. In [env/swarm_env.py](../env/swarm_env.py), a collision with a wall or obstacle causes the proposed move to be rejected entirely, so the agent does not advance at all for that step. If the observation after that collision still looks similar, the greedy policy can choose the same action again and effectively pin itself in place or in a short turn-loop. The action space also includes non-forward actions such as turn-in-place and zero-throttle variants, so a partially trained policy can settle into safe but unproductive behavior instead of pushing through to the task. This is more common with weak or short training runs, because [train/independent_dqn_pytorch.py](../train/independent_dqn_pytorch.py) uses epsilon-greedy exploration during training but the demo removes that randomness completely. In practice, the strongest fixes are: train longer or with better checkpoints, add a tiny amount of evaluation-time exploration or tie-breaking noise, or adjust rewards so idle/oscillatory behavior is less attractive than progress.

## Q: What decides when `train/demo.py` resets into another randomly generated environment?
A: The demo resets only when the environment reports that the current episode has ended. In [train/demo.py](../train/demo.py), each backend checks `terminated = any(terminations.values())` and `truncated = any(truncations.values())`, then calls `env.reset(seed=next_reset_seed)` only if either one is true. Those flags come from [env/swarm_env.py](../env/swarm_env.py): `terminated` becomes true when all targets are gone and no agent is still carrying food, and `truncated` becomes true when `self.step_count >= self.cfg.max_steps`. So the demo moves on to a new random environment only after the swarm finishes the task or hits the episode step limit. The global `--max-steps` flag in `demo.py` is different: that one exits the demo process entirely after N rendered steps rather than resetting the environment.

## Q: Is the solution to demo-time “stuck” behavior just to train for longer?
A: Longer training is the first thing to try, but it is not the whole answer. In this repo, [train/demo.py](../train/demo.py) runs the policy greedily with no exploration, so any local habit the network learned gets repeated exactly. More training usually helps because the Q-values become less noisy and the policy has more chances to learn escape behavior, but a weak reward structure or brittle action design can still leave the demo stuck in collisions or turn-loops even after additional training. In the current setup, the most practical order is: first train longer and use fresh checkpoints; if that is still not enough, then add a small demo-time epsilon, stronger anti-idle shaping, or a simple stuck-recovery heuristic in the runtime. So training longer is necessary to test before changing the design, but it is not guaranteed to fully solve the behavior on its own.

## Q: How do I make training do more exploration at the beginning using the new schedule flags?
A: Use the epsilon-schedule CLI flags in [train/independent_dqn_pytorch.py](../train/independent_dqn_pytorch.py): `--epsilon-start`, `--epsilon-final`, `--epsilon-decay-steps`, and `--warmup-steps`. To make the beginning more exploratory, keep `--epsilon-start 1.0`, increase `--epsilon-decay-steps` so epsilon stays high for longer, and usually increase `--warmup-steps` so the replay buffer fills with more random experience before learning starts. A good example is `python train/independent_dqn_pytorch.py --headless --total-steps 30000 --epsilon-start 1.0 --epsilon-final 0.05 --epsilon-decay-steps 20000 --warmup-steps 2000`. That means the policy starts fully random, stays fairly random across much of training, then gradually becomes more greedy later.

## Q: Why can a demo robot still look a little frozen even when it is not physically boxed in?
A: Because "not boxed in" is not the same as "the policy knows a better next action." In [train/demo.py](../train/demo.py), the demo uses pure `argmax`, so if the network slightly prefers a stop/turn action it will repeat it exactly. The observation is also purely reactive and local in [env/swarm_env.py](../env/swarm_env.py): lidar, local target/nest vectors, neighbor vector, speed, and pheromone samples, with no memory of being stuck recently. [models/q_network.py](../models/q_network.py) is just a feed-forward MLP, so it cannot remember that it has been oscillating in place for several steps. The action space in [env/swarm_env.py](../env/swarm_env.py) also includes zero-throttle and turn-in-place actions, and the per-step penalty in [env/config.py](../env/config.py) is only `-0.01`, so there is not a very strong incentive to break out of a locally "safe" low-motion behavior. The result is that a policy can look mildly frozen even in open space if its local observations and Q-values keep favoring a cautious loop rather than decisive forward progress.

## Q: Should the observation include the trajectory, such as all past steps or a sliding window?
A: Not all past steps. A full trajectory history is usually the wrong tool here because it blows up the observation size, makes training harder, and is unnecessary for this kind of local swarm policy. But a short history can help. In this codebase, the current observation in [env/swarm_env.py](../env/swarm_env.py) is memoryless, and the policy in [models/q_network.py](../models/q_network.py) is a feed-forward MLP, so the agent cannot directly detect "I have been oscillating here for several steps." The practical improvement is a small sliding window or a few derived temporal features, such as recent displacement, recent heading change, last action, or "progress toward target over the last N steps." Those usually capture the benefit of trajectory information without the cost of carrying the entire path. So the best recommendation is: do not include the full trajectory; if needed, add a short temporal summary or sliding window.

## Q: Can the simulator be limited so agents only sense pheromone within the same bounded radius used by Mission Control?
A: Yes. The simulator already sampled pheromone only at the same three forward offsets that Mission Control uses, but that radius is now made explicit in the code. In [env/config.py](../env/config.py), `pheromone_sample_spacing_scale = 1.5` now defines the sample spacing, and [env/swarm_env.py](../env/swarm_env.py) derives both the forward sample distances and the awareness radius from it. With the defaults (`pheromone_samples = 3`, `agent_radius = 7.0`, spacing scale `1.5`), the farthest sensing distance is `31.5` world units, matching the Mission Control awareness radius formula. Pheromone outside that bounded forward sensing radius does not affect the observation.

## Q: How do I fix the frozen-looking robot behavior in demo/runtime?
A: In this repo, the fix order should be pragmatic rather than theoretical. First, retrain with the current observation/action contract and give the policy more exploration early in training using the exposed epsilon schedule in [train/independent_dqn_pytorch.py](../train/independent_dqn_pytorch.py); weak checkpoints are the most common cause of low-motion loops. In the current codebase, a short observation history has already been added, so the next most practical change after retraining is a tiny amount of demo/runtime exploration rather than a major architecture rewrite.

## Q: Is shared policy or independent policy more optimal in this repo?
A: Usually shared policy is the better first choice for this swarm setup, but it is not universally better. In [train/independent_dqn_pytorch.py](../train/independent_dqn_pytorch.py), `--shared-policy` makes all agents reuse the same [QNetwork](../models/q_network.py) weights while still acting from their own local observations. That tends to be more sample-efficient, easier to stabilize, and a better fit when the robots are homogeneous and should learn the same local behavior. Independent policies can be more expressive because each agent can specialize, but they are also harder to train, need more data, and can overfit to agent index rather than role-free swarm behavior. For the current codebase, where agents are symmetric and the main issue is policy quality rather than intentional role specialization, shared policy is the more pragmatic default; switch to independent policies only if you have evidence that role specialization actually helps the task.

## Q: Can I stop using `checkpoints_new` and just keep updating `checkpoints/`?
A: Yes. The custom trainer in [train/independent_dqn_pytorch.py](../train/independent_dqn_pytorch.py) writes fixed filenames directly into the chosen `--save-dir`: `metadata.json` plus either `shared.pt` or `agent_0.pt`, `agent_1.pt`, and so on. That means you can point training straight at `checkpoints/` and let new runs overwrite the old files in place. The only reason to keep a separate directory like `checkpoints_new` was to avoid mixing incompatible old checkpoints with the newer observation/action contract. If you no longer need the legacy files, reusing `checkpoints/` is fine.

## Q: If all robots use the same shared policy, why do only some of them get stuck?
A: Shared policy means shared weights, not shared behavior. In this repo, each agent still receives its own local observation from [env/swarm_env.py](../env/swarm_env.py): different lidar readings, different target/nest vectors, different neighbor geometry, different pheromone samples, different heading, and different recent observation history. The shared [QNetwork](../models/q_network.py) applies the same mapping to each agent’s input, but if the inputs differ, the chosen actions can differ too. So one robot may fall into a weak local loop while another, seeing slightly different geometry or history, keeps moving. This is normal in a homogeneous shared-policy swarm: the policy is the same, but each agent’s state in the world is not.

## Q: Are the lidar readings based on the surrounding simulation?
A: Yes. In [env/swarm_env.py](../env/swarm_env.py), `_lidar_scan()` casts rays from each agent into the current simulated world, and `_ray_distance()` marches each ray forward until it hits either a world boundary or an obstacle rectangle. The returned lidar values are therefore derived from the actual surrounding simulation geometry at that moment, not from a placeholder pattern. One important limitation is that the current lidar does not treat other agents or targets as ray-cast obstacles; it only reacts to walls and obstacle rectangles.

## Q: Is there currently a sliding-window observation history implemented, and where is it?
A: Yes. The main switch is `observation_history_steps = 3` in [env/config.py](../env/config.py). In [env/swarm_env.py](../env/swarm_env.py), the environment allocates `self._obs_history`, computes `obs_dim` as `single_obs_dim * observation_history_steps`, fills the history on reset via `_get_obs(reset_history=True)`, and on each step shifts the history buffer and appends the newest frame in `_get_obs()`. The single-frame builder is `_get_obs_frame()`, while `_get_obs()` returns the flattened stacked history. The robot runtime mirrors the same contract in [firmware/run.py](../firmware/run.py) using `observation_history_steps`, `build_single_observation(...)`, and `build_observation_history(...)`.

## Q: In `train/demo.py`, can agents choose to lay pheromone?

The actual deposit happens in `_update_pheromone()` in [env/swarm_env.py](../env/swarm_env.py), which checks the chosen action’s deposit flag before writing to the pheromone grid.

## Q: How do I run training with epsilon-greedy exploration?
A: Use the epsilon schedule flags on [train/independent_dqn_pytorch.py](../train/independent_dqn_pytorch.py): `--epsilon-start`, `--epsilon-final`, `--epsilon-decay-steps`, and `--warmup-steps`. For example, `python train/independent_dqn_pytorch.py --headless --shared-policy --total-steps 30000 --save-dir checkpoints --epsilon-start 1.0 --epsilon-final 0.05 --epsilon-decay-steps 20000 --warmup-steps 2000` starts fully random, keeps exploration high for much of training, and then gradually becomes greedier. ## Q: Why is the policy still not “finding food” even if `food_detection_radius` is set to `1000`?
A: Because that radius does not directly mean “successful food interaction,” and making it enormous can actually make the food signal less useful. In [env/swarm_env.py](../env/swarm_env.py), `food_detection_radius` only affects the binary local cue from `_food_presence()` and the shaping logic in `_compute_detectable_food_state()` / `_apply_food_shaping()`. But the trainer’s `food_retrieved` metric in [train/independent_dqn_pytorch.py](../train/independent_dqn_pytorch.py) is actually incremented from `info["food_delivered"]`, not from detection or pickup. So a run can have food detected everywhere and still show `food_retrieved = 0` if agents never overlap food closely enough to pick it up or never bring carried food back to the nest. Also, with a radius as large as `1000` in a `900x600` world, the binary `food_presence` feature is effectively always `1` whenever any food exists, which removes its local meaning and can make it a weaker learning signal rather than a better one.

## Q: What are the current rewards and punishments, and where are they defined?
A: The scalar reward coefficients are defined in [env/config.py](../env/config.py) under the `# Rewards` section. The environment applies them in [env/swarm_env.py](../env/swarm_env.py) inside `step()`, `_handle_targets()`, `_handle_nest_delivery()`, `_apply_exploration_reward()`, `_apply_food_shaping()`, and `_apply_pheromone_reward()`. The current defaults are: `reward_step = -0.01` per step, `reward_collision = -0.2` on collision, `reward_pheromone_deposit_cost = -0.02` when the action requests a pheromone deposit, `reward_pickup = 1.5` on pickup when nest delivery is required, `reward_target = 8.0` for direct target collection when nest delivery is not required, `reward_nest_delivery = 10.0` on delivery, `reward_new_cell = 0.02` for first-time visited coverage cells, `reward_food_approach = 0.2` scaled by progress toward detectable food, `reward_food_detected = 0.05` when food first enters local detection range, `reward_pheromone_follow = 0.03` scaled by forward pheromone gradient, and `reward_pheromone_following = 0.0` for the older usage-based pheromone shaping term (currently off by default). The per-step reward breakdown is exposed in `info["reward_breakdown"]` from `step()` and logged into episode metrics by [train/independent_dqn_pytorch.py](../train/independent_dqn_pytorch.py).

## Q: Where are `ParallelEnv` and PettingZoo used in this repo, and how?
A: The core environment class [env/swarm_env.py](../env/swarm_env.py) inherits from `pettingzoo.ParallelEnv`, so PettingZoo defines the main environment interface. That is why the env exposes `possible_agents`, `agents`, `observation_space(agent)`, `action_space(agent)`, `reset()`, and `step(actions)` with dicts keyed by agent id. The custom training, demo, and evaluation paths use that API directly by reading `env.possible_agents`, building per-agent action dicts, and consuming per-agent observation/reward/termination dicts. PettingZoo is also used indirectly through wrappers for library backends: [train/sb3_dqn.py](../train/sb3_dqn.py) converts the PettingZoo env with `supersuit.pettingzoo_env_to_vec_env_v1(...)`, and [train/rllib_dqn.py](../train/rllib_dqn.py) wraps it with RLlib’s `ParallelPettingZooEnv(...)`. So PettingZoo is the environment contract that everything else in the repo is built around.

## Q: What is the recommended plan to turn the current RL stack into a stronger best-of-breed existing approach for this problem?
A: The recommended path is: first upgrade the current DQN into a much stronger baseline with Double DQN, dueling heads, prioritized replay, n-step returns, and ideally a distributional variant; then add proper recurrent rollout support; then implement **recurrent MAPPO with parameter sharing and centralized training / decentralized execution** as the main target algorithm; and finally add a cooperative value-decomposition baseline such as QMIX for comparison. The reasoning and phased plan are documented in [docs/best_rl.md](best_rl.md).

## Q: What is the total amount of food in the environment during training?
A: Per episode, the total food available is `n_targets`. With the current defaults, that is 4 food targets. They are spawned on reset (`_spawn_targets()`), removed when picked up in `_handle_targets()`, and are not respawned within the same episode. Across an entire training run, food is therefore unbounded over time because each new episode resets and spawns a fresh set of `n_targets` again. You can change the per-episode amount with `--n-targets` in the trainer CLI.

## Q: Where can I find the current rewards?
A: The source-of-truth reward values are in [env/config.py](../env/config.py) under the `# Rewards` section. The reward logic is applied in [env/swarm_env.py](../env/swarm_env.py), mainly in `step()` and helper methods such as `_handle_targets()`, `_apply_food_shaping()`, `_apply_exploration_reward()`, and `_apply_pheromone_reward()`. If you want to see per-episode reward components during training, check the reward-breakdown logging fields in [train/independent_dqn_pytorch.py](../train/independent_dqn_pytorch.py).

## Q: Why does the pheromone look like it comes from the goal instead of being laid by the robots?
A: In the current simulator code, pheromone is laid by the robots at their current grid cell, not spawned from the goal. The relevant write happens in `_update_pheromone()` in [env/swarm_env.py](../env/swarm_env.py), which converts each agent's current `(x, y)` into a pheromone-grid cell and increments that cell. What makes it look goal-originated is the current gating rule: `pheromone_requires_food = True` in [env/config.py](../env/config.py), so agents do not deposit while exploring. They only begin depositing after pickup, when `_handle_targets()` marks `agent.carrying_food = True`. That means the first visible pheromone cells appear at or near the food location, and then the trail continues as the carrying robot moves. Decay and diffusion can reinforce that visual impression, but the source cell each step is still the robot's position.

## Q: Why can `demo.py` seem to find food while training looks like it never does?
A: The main reason is that the trainer's printed `food` number is not “food encountered” or even “food picked up”; it is **food delivered to the nest**. In [train/independent_dqn_pytorch.py](../train/independent_dqn_pytorch.py), the console log prints `episode_food_retrieved`, which is accumulated from `info["food_delivered"]` after each step. But the environment separately tracks pickups in `info["targets_collected"]` inside [env/swarm_env.py](../env/swarm_env.py). So if agents reach food and pick it up but fail to return to the nest, the demo can visibly look like food is being found while the training console still prints `food 0`. There is also a policy-mode difference: training uses epsilon-greedy exploration, while [train/demo.py](../train/demo.py) runs a deterministic greedy policy with `argmax`, so the trajectories are not directly comparable step-for-step.

## Q: Why do pheromones keep expanding without stopping in the simulator?
A: The current pheromone update rule in [_update_pheromone()](../env/swarm_env.py) has two properties that make the field keep spreading. First, diffusion uses `np.roll(...)` to get the four neighbors, which wraps the grid at the edges instead of treating the borders as hard boundaries, so pheromone leaving one side re-enters from the opposite side. Second, there is no floor/threshold that zeroes out very small values after decay, so once a little mass diffuses into a cell it can remain nonzero for a long time. With `pheromone_decay = 0.985` and `pheromone_diffuse_rate = 0.25` in [env/config.py](../env/config.py), repeated robot deposits plus wraparound diffusion make the heatmap look like it expands indefinitely. The decay itself is applied, but not strongly enough to visibly stop the spread when deposits continue and tiny residual values are never clipped away.

## Q: Why do pheromones look like they are just popping out instead of being dropped continuously?
A: In the simulator, pheromone is not rendered as a continuous particle trail. It is deposited into a discrete grid cell after the action has already moved the agent, inside `_update_pheromone()` in [env/swarm_env.py](../env/swarm_env.py). The deposit location is computed by snapping the robot's current `(x, y)` to a pheromone cell using `gx = int(agent.x // cell)` and `gy = int(agent.y // cell)`, then incrementing that whole cell. Rendering in `_draw_pheromone()` also draws full grid rectangles and normalizes their color by the current grid maximum. So the visual effect is: move first, then a cell under the new robot position lights up strongly relative to the rest of the field. That makes the pheromone appear to “pop out” at discrete spots rather than looking like a smooth analog drip, even though it is still being laid by the robot.

## Q: Where is the actual DQN implementation in this repo?
A: The main custom DQN implementation is in [train/independent_dqn_pytorch.py](../train/independent_dqn_pytorch.py). The hyperparameters live in `DQNConfig`, the replay memory is `ReplayBuffer`, epsilon scheduling is `linear_schedule(...)`, network creation happens where `QNetwork(obs_dim, action_dim)` and target networks are initialized, action selection is the epsilon-greedy block in the main training loop, and the Bellman update is the section computing `q_vals`, `max_next`, `target`, and the Huber loss before `optimizer.step()`. The actual Q-network architecture itself is defined separately in [models/q_network.py](../models/q_network.py) as a small MLP that maps observations to one Q-value per discrete action.

## Q: What is the difference between `reward_target` and `reward_pickup`, and are they team-wide or per-agent?
A: In [env/swarm_env.py](../env/swarm_env.py), both rewards are applied only to the collecting agent (`rewards[collected_by] += ...`), not broadcast to all agents. The switch is task mode: when `require_nest_delivery` is true and nest is enabled, pickup gives `reward_pickup` and later nest return gives `reward_nest_delivery`; when nest delivery is not required, collection gives `reward_target` immediately. So `reward_target` and `reward_pickup` are both per-agent collector rewards, chosen by task configuration.

## Q: Why can `evaluate.py` look like it never ends and just sit there?
A: In the current evaluator implementation in [analysis/evaluate.py](../analysis/evaluate.py), evaluation is intentionally silent during the episode loop: it writes CSV rows only after each episode and does not print per-step or per-episode progress. It also forces `target_respawn = True`, so episodes do not terminate early by clearing all targets; instead they run until the fixed horizon `cfg.max_steps`. In [env/swarm_env.py](../env/swarm_env.py), that means the loop only stops when `self.step_count >= self.cfg.max_steps`, which becomes a truncation. So if you run with several episodes and a large `--eval-steps`, the process can appear to “hang” even though it is still working. For a quick test, lower the workload explicitly, for example: `./.venv/bin/python train/evaluate.py --episodes 1 --eval-steps 50 --headless ...`.

Matplotlib does not draw markers or connecting segments for `NaN`, so the `*_time_to_first_discovery_vs_agents` plot shows missing points at swarm sizes where that condition never discovered a target in the sampled episodes.

## Q: Is the same per-agent inefficiency also part of why `analysis/evaluate_comparison.py` is slow?
A: Yes, partly. In [analysis/evaluate_comparison.py](../analysis/evaluate_comparison.py), `_run_episode()` still does per-agent inference in a Python loop, creating a tensor and running a forward pass separately for each agent on every step. So the same kind of non-batched policy inference overhead that slowed the old shared-policy training path also exists in comparison evaluation. But it is not the whole story, and probably not even the biggest part. The larger reason comparison runs feel slow is that the script executes a full nested sweep across 4 conditions, many swarm sizes, and multiple episodes per size, then writes raw CSVs, summary CSVs, exploration visuals, and multiple matplotlib plots. So the accurate answer is: yes, the same per-agent inference pattern contributes, but `evaluate_comparison.py` is also fundamentally slow because it is doing a large amount of total evaluation work and output generation by design.

## Q: How do I run `train/demo.py` for a specific filename or folder name?
A: `train/demo.py` does not load checkpoints by `--filename` directly. It loads from `--checkpoint-dir`, so for a specific saved training name you point it at that run's checkpoint folder, usually `checkpoints/<folder_name>/full_policy`. ## Q: Should there be a punishment for moving away from the target so agents cannot exploit a closer/farther loophole?
A: In this repo, probably yes, but it should be small and symmetric rather than a large standalone penalty. Right now [_apply_food_shaping()](../env/swarm_env.py) only gives shaping reward when the current detectable-food distance is smaller than the previous one, and gives nothing when the agent moves farther away. That means oscillating or looping behavior is not directly canceled out by the shaping term itself. A cleaner design is to make the shaping use **signed distance progress**, such as a reward proportional to `(prev_dist - curr_dist)`, so moving closer gives a positive value and moving away gives an equally scaled negative value. That closes the loophole more cleanly than adding a separate arbitrary punishment. The caution is that the negative term should stay small, because agents sometimes must temporarily move away due to turning radius, obstacle avoidance, or swarm interactions. In practice, the best version is usually: small signed progress reward, clipped to a reasonable range, optionally with a deadband for tiny distance changes.

## Q: Will this reward shaping actually help real-world object finding if the robot does not get that reward at runtime?
A: Yes, potentially, but only as a **training aid**, not because the reward itself exists in deployment. In this repo, the signed food-approach term in [_apply_food_shaping()](../env/swarm_env.py) is environment-side reward shaping only; it is not part of the observation vector or action interface. So in the real world, the robot would not need to receive that reward online for the learned policy to still be useful. The policy can still benefit if the shaping helped training converge toward behaviors that are already supported by real sensor inputs. The limitation is important: if the shaping reward depends on simulator-only hidden information that the real robot cannot infer from its sensors, then the learned behavior may not transfer well. So the safe interpretation is: this kind of shaping can help training learn better search behavior, but sim-to-real success still depends on whether the observation vector contains real, physically available cues that let the robot reproduce that behavior without access to the simulator's reward signal.

## Q: Are there any concrete bugs in the pheromone placement/update logic?
A: Yes. Two important issues exist in the current simulator path. First, [_update_pheromone()](../env/swarm_env.py) does not skip `failed_agent_indices`, so a failed agent can still deposit pheromone if its sampled action has the deposit bit set, even though the movement/reward path treats failed agents as inactive. Second, the deposit cost is charged earlier in `step()` whenever the action requests deposit, even if no pheromone is actually deposited because pheromone is disabled or `pheromone_requires_food` blocks it. So the current logic can penalize a deposit attempt without creating any pheromone, and can let failed agents write pheromone unexpectedly.

## Q: If agents move for a few seconds and then freeze, is that more likely a system error or an RL training problem?
A: In the current repo configuration, it is more likely an **RL training / reward-design problem** than a system fault. The environment does allow stop-like actions because the action table includes `throttle = 0.0` in [_build_action_table()](../env/swarm_env.py), so the policy can legitimately learn to stop. With the current reward settings in [env/config.py](../env/config.py), the agent gets a strong per-step penalty and strong collision penalty, while many shaping rewards are set to zero (`reward_new_cell`, `reward_food_approach`, `reward_food_detected`, `reward_pheromone_follow`, `reward_pheromone_following`, and `reward_nest_delivery`). That makes the task quite sparse: the main positive reward only arrives at pickup, so a learned policy can collapse toward “do nothing risky” behavior after initial motion. A true system error would look more like episode termination, failed-agent logic, or physics/state updates stopping entirely. But if the agents simply stop choosing forward-motion actions while the episode continues, that is usually the policy learning a conservative local optimum, not the simulator breaking.

## Q: What does `episode_logger` do?
A: `episode_logger` is a `CSVLogger` that writes one row per completed training episode to `episode_metrics.csv` in the current run directory. It is initialized with the output schema (episode index, epsilon, reward totals, food/coverage/collision metrics, and reward-breakdown components), receives data at episode end via `episode_logger.log(episode_row)`, and is closed in the `finally` block to flush and release the file handle.

## Q: Why does using `--no-pheromone` in `train/demo.py` make pheromones look more prominent?
A: Because `train/demo.py` does **not** actually define a `--no-pheromone` flag. Through [train/experiment_utils.py](../train/experiment_utils.py), the real flags are `--no-use-pheromone` and `--no-pheromone-requires-food`. Python `argparse` allows long-option prefix matching by default, so `--no-pheromone` is likely being interpreted as `--no-pheromone-requires-food`, not as “disable pheromone.” That changes the behavior in the opposite direction: it turns off the food-carrying gate for deposition, so agents can lay pheromone during ordinary exploration, which makes the pheromone heatmap appear much more prominent. If you actually want pheromone disabled in demo, use `--no-use-pheromone` or `--pheromone-disabled`.

A: Yes. ## Q: Are the training and demo environments actually the same, and why can demo perform much worse?
A: They use the same underlying environment class, [env/swarm_env.py](../env/swarm_env.py), and both training and demo build config through [train/experiment_utils.py](../train/experiment_utils.py). So the codepath is largely the same. But the important catch is that [train/demo.py](../train/demo.py) does **not** load the original training environment settings from checkpoint metadata. It just uses the current CLI defaults unless you pass matching flags by hand. That means demo can silently run under different settings from training, especially for `--use-pheromone`, `--pheromone-requires-food`, `--target-respawn`, `--active-targets`, `--dynamics-mode`, `--n-agents`, and any other env overrides exposed through `add_env_config_args(...)`. The checkpoint metadata currently stores only limited fields such as `use_pheromone` and `shared_policy`, and demo does not automatically apply even those. So if demo looks much worse, the most likely reason is not that training and demo use different environment code, but that demo is running the same code under different environment settings than the policy was trained on.

## Q: Is `analysis/evaluate_comparison.py` fully optimized?
A: No, not yet. The comparison runner is still functional, but it still has the old per-agent inference hot path in `_run_episode()`: it loops over agents, creates a tensor per agent with `torch.tensor(...)`, runs one forward pass per agent, and only then builds the action dict. So the same batching optimization that was added to the shared-policy training path has **not** been applied to `analysis/evaluate_comparison.py` yet. The script is also inherently expensive because it runs a full nested sweep over conditions, agent counts, and episodes, then writes CSVs and plots. So the honest answer is: it is partially understood and a prompt exists for optimizing it, but the implementation is not fully optimized today.

## Q: Why can training show food pickup while demo never picks up food?
A: The biggest reason is that training and demo use **different action-selection behavior** even when they load the same model weights. In [train/independent_dqn_pytorch.py](../train/independent_dqn_pytorch.py), training uses **epsilon-greedy exploration**, so episode metrics such as food pickup include many random exploratory actions early and mid training. In [train/demo.py](../train/demo.py), demo uses pure greedy `argmax` actions with no epsilon, so it shows only what the learned policy itself does deterministically. That means “pickup during training” does **not** automatically imply the greedy final policy has learned to pick up food. A second cause can make demo even worse: [train/demo.py](../train/demo.py) does not restore the training-time environment settings from checkpoint metadata, so mismatches in flags like pheromone usage, respawn, active target count, dynamics mode, or agent count can further degrade demo performance.

## Q: Can demo be run with some random exploratory behavior instead of pure greedy actions?
A: Yes. [train/demo.py](../train/demo.py) now supports `--demo-epsilon`, which adds epsilon-style random action selection during demo. For example, `python train/demo.py --checkpoint-dir checkpoints/my_run/full_policy --shared-policy --demo-epsilon 0.1` makes each action random with probability `0.1` and greedy otherwise. This is useful when you want demo behavior closer to training-time epsilon-greedy exploration instead of strict deterministic `argmax`.

## Q: Can `train/demo.py` run a fully random policy baseline?
A: Yes. [train/demo.py](../train/demo.py) now supports `--backend random`, which ignores checkpoints and samples random discrete actions directly from the current environment action space. For example: `python train/demo.py --backend random --max-steps 200`. This is useful as a quick visual baseline without going through `analysis/evaluate_comparison.py`.

## Q: Is the environment actually randomized during training?
A: Yes, at the **episode reset** level. In [train/independent_dqn_pytorch.py](../train/independent_dqn_pytorch.py), training resets the environment with `seed=args.seed` initially and then increments the seed on each episode reset via `next_reset_seed += 1`. In [env/swarm_env.py](../env/swarm_env.py), `reset()` rebuilds obstacles, nest position, targets, agent spawn positions, failed-agent assignment, and the optional mixed dynamics choice from the environment RNG. So training does randomize the world across episodes. The important caveat is that this is **not** continuous randomization inside a single episode; the main world randomization happens when `reset()` is called. Within an episode, stochasticity mainly comes from epsilon-greedy action selection and any configured observation/dynamics noise.

## Q: Why do the agents move back and forth for no obvious reason?
A: In this repo, that behavior is usually a policy/reward/control issue, not a low-level simulator failure. The action space in [env/swarm_env.py](../env/swarm_env.py) is very coarse: each action chooses `throttle` from `{-1, 0, 1}` and `turn` from `{-1, 0, 1}`, so the learned controller is effectively doing bang-bang control rather than smooth steering. On top of that, the current reward shaping can create local oscillation incentives: signed food-approach reward reacts to short-term distance change, there is no explicit penalty for action switching or reverse/turn jitter, and the policy only sees a short observation history rather than a true memory state. The result is that agents can learn small forward/backward or turn/untun loops that locally preserve value without making meaningful task progress. If this happens in demo with `--demo-epsilon > 0`, random exploratory actions can make it even more visible. So the likely causes are coarse discrete actions, short-horizon shaping, and no smoothness/inertia penalty in the reward, rather than a pure system bug.

## Q: Is the nearest-target observation now global or local-only?
A: It is local-only and now tied to actual detectability. [env/swarm_env.py](../env/swarm_env.py) only exposes nearest-target features if the target is both within `cfg.lidar_max_range` and not blocked by obstacles along the line of sight. The target block now includes four values instead of two: body-frame `dx`, body-frame `dy`, normalized target distance, and normalized relative angle. When no target is detectable, all four values are zero, and `food_presence` is also zero.

## Q: What is the current observation space and action space, and where are they defined?
A: They are defined in [env/swarm_env.py](../env/swarm_env.py). The observation space is a `gymnasium.spaces.Box(low=-1.0, high=1.0, shape=(obs_dim,), dtype=np.float32)` created in `observation_space()` and `_compute_obs_dim()`. With the current defaults, one observation frame has 23 features and `observation_history_steps = 3`, so the flattened per-agent observation size is **69**. The frame contents are assembled in `_get_obs_frame()` as: 9 lidar values, 2 nearest-target values, 2 nest-direction values, 2 nearest-neighbor values, 2 heading values, 1 speed value, 1 food-presence value, 1 carrying-food value, and 3 pheromone samples. The action space is `gymnasium.spaces.Discrete(cfg.num_actions)` with `num_actions = 18`, and the discrete action table is built in `_build_action_table()` from all combinations of `throttle in {-1, 0, 1}`, `turn in {-1, 0, 1}`, and `deposit in {0, 1}`.

## Q: Why does MAPPO show food still at 0 during training?

A: There were two issues. ## Q: Why do the agents move at the start and then just stop?

## Q: What are the online Q-network and target Q-network, and why do we need both?

A: In the DQN trainer, the **online Q-network** is the one actively being trained by gradient descent and used to estimate current action values. The **target Q-network** is a slower-moving copy used only to compute the Bellman bootstrap target for the next state. In [train/independent_dqn_pytorch.py](../train/independent_dqn_pytorch.py), the online network computes `Q(s, a)` and the target network computes the `max_a' Q_target(s', a')` term inside the TD target; then the target network is periodically synced from the online network. The reason for using both is stability: if the same network is used both to predict and to define the target every step, the target keeps moving too quickly and training becomes much less stable.

## Q: How are obstacles and food placed in the environment?

A: Placement happens during `reset()` in [env/swarm_env.py](../env/swarm_env.py), in this order: obstacles, nest, targets, then agents. Obstacles are generated by `_spawn_obstacles()` as random non-overlapping rectangles with random width/height and random positions inside the arena margins. The nest is placed by `_spawn_nest()` using `_sample_free_position(self.cfg.nest_radius)`, so it avoids obstacles and borders. Targets are created by `_spawn_targets()`, which clears `self.targets` and calls `_respawn_targets(...)`; each target position is also generated by `_sample_free_position(self.cfg.target_radius)`. Agents are then placed by `_spawn_agents()`, again through `_sample_free_position(self.cfg.agent_radius)`, and each agent also gets a random heading. `_sample_free_position()` is the common placement rule: it tries up to 200 random points and rejects any candidate that overlaps an obstacle, the nest clearance radius, an existing target, or an existing agent.

## Q: How does the current target-delivery loop work?

A: In the current environment implementation in [env/swarm_env.py](../env/swarm_env.py), an agent may carry at most one food item at a time because `_handle_targets()` skips pickup for agents that already have `carrying_food = True`. A completed delivery is counted only when `_handle_nest_delivery()` sees a carrying agent reach the nest; that clears `carrying_food`, increments `food_delivered`, and awards `reward_nest_delivery`. In demo/rendered mode, carrying agents now switch to a distinct green-highlighted color and return to the normal body color after delivery.

## Q: How can we train delivery more effectively?

A: The most effective changes are usually about curriculum pressure and reward balance, not adding more mechanics. Third, increase total steps substantially, because the current full curriculum spreads the budget across multiple stages. If delivery is the priority, good defaults to try are: longer training, lower pickup reward, higher delivery reward, stronger undelivered penalty, and evaluating stage1/stage1_to_2 separately before moving to `full`.

## Q: What is the recommended full training command, and what does each argument mean?

A: A solid current full-run command for the MAPPO path is:

```bash
python train/train.py --backend mappo --headless --curriculum full --n-agents 6 --total-steps 600000 --rollout-steps 128 --update-epochs 4 --minibatch-size 256 --eval-every 10000 --eval-episodes 5 --reward-pickup 8 --reward-nest-delivery 30 --reward-undelivered-food -5 --folder-name mappo_full_600k
```

What each argument does:

- `python train/train.py`
  - runs the top-level training entrypoint for the repo

- `--backend mappo`
  - selects the recurrent MAPPO trainer instead of the custom DQN, SB3, or RLlib paths

- `--headless`
  - disables the PyGame window during training so the run is faster and better suited to long jobs

- `--curriculum full`
  - uses the full staged MAPPO curriculum rather than only the early stages
  - this means training progresses through the single-agent, small-swarm, and full-swarm stages

- `--n-agents 6`
  - sets the target full-swarm size for the later curriculum stages
  - the earlier curriculum stages still override this downward when they intentionally train with fewer agents

- `--total-steps 600000`
  - sets the total amount of training across the full curriculum
  - this is the biggest reason the command is considered a more serious run than a short or medium smoke run

- `--rollout-steps 128`
  - each on-policy MAPPO update collects rollouts in chunks of 128 env steps before optimization

- `--update-epochs 4`
  - after each rollout, PPO-style updates are run for 4 passes over that collected batch

- `--minibatch-size 256`
  - controls the minibatch size used during PPO optimization over the rollout data

- `--eval-every 10000`
  - runs periodic evaluation every 10,000 training steps
  - this does not change the learning rule directly, but it gives useful progress checkpoints during long runs

- `--eval-episodes 5`
  - each scheduled evaluation uses 5 evaluation episodes instead of just 1
  - this makes eval less noisy

- `--reward-pickup 8`
  - keeps pickup meaningful, but still smaller than full delivery

- `--reward-nest-delivery 30`
  - makes successful return-to-nest delivery the strongest core task reward

- `--reward-undelivered-food -5`
  - penalizes ending an episode while still carrying food
  - this helps discourage “pick up but never bring it home” behavior

- `--folder-name mappo_full_600k`
  - controls the output/checkpoint naming
  - checkpoints will go under `checkpoints/mappo_full_600k/`
  - run logs will use the same base name

Why this command is recommended:

- it keeps the current default PPO/MAPPO optimizer settings that already match the trainer
- it gives the curriculum enough total budget that the later hard stages are not starved
- it preserves the current reward ordering of pickup < delivery
- it gives you periodic evaluation during the run instead of training blind

What it is not:

- it is not guaranteed to produce a perfect policy
- it is not the only valid command
- it is a practical strong starting point for the current repo, not a proof of optimality
